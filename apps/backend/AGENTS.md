# apps/backend

- Hono, runtime-agnostic: routes, middleware, services, repositories and DAO interfaces, with no entrypoint and no runtime-specific APIs or dependencies (type-checked against web-standard `webworker` lib types only). It runs through a runtime package (`apps/backend-*`, listed in the root `AGENTS.md`) that imports it and owns the entrypoint; see that package's `AGENTS.md` for runtime-specific rules (secrets, dev/deploy, datastore DAOs).
- Request handling is layered: route (`src/app.ts`) → service (`src/service/*.service.ts`) → repository (`src/repository/*.repository.ts`) → DAO (`src/dao/*.interface.ts`; the D1/R2 implementations live in the runtime package's `src/dao/`). A route depends only on a service; a service holds business logic (permissions, limits, validation across fields) and is the only layer that decides "not found" / validation outcomes; a repository maps a DAO's raw storage rows (snake_case, `src/dao/records.ts`) to domain entities (camelCase, `repository/case.ts`); only the DAO layer talks to a datastore, behind an interface.
- Writes: one user operation = one `StoreRepository.commit(bumps, mutations)` = one D1 `batch` (a transaction). `bumps` raises the revision of each sync unit touched (`users.rev` / `groups.rev`, docs/spec.md "データ取得・同期") and every synced row written gets that revision via `revOf`. Build mutations with the helpers in `repository/store.repository.ts` (`insert`, `update`, `softDelete`, `softDeleteTree`, ...); never write synced rows outside `commit`.
- No in-memory DAOs for the D1 tables: services are tested with hand-written fakes of the repository, and the DAOs plus the whole wiring are tested against a local D1/R2 in the runtime package (`apps/backend-worker`).
- Errors: services throw `AppError(code)` (`src/errors.ts`); `app.onError` maps the code to its HTTP status and answers `{ error: code }` (plus `limit` for `LIMIT_EXCEEDED`). Request shapes are validated with zod schemas in `src/validation.ts` (trimmed, lengths counted with `charLength`), answering `{ error: 'VALIDATION' }`.
- Every route is served under `/api` (`basePath('/api')` in `src/app.ts`): the frontend is served at `/` on the same origin (Vite's dev proxy forwards `/api` locally), so there's no CORS middleware. Paths seen by middleware (`c.req.path`, `auth.excludePaths`) include the `/api` prefix.
- `src/app.ts` exports the Hono app instance's type (`AppType`) for Hono RPC. This is the API contract — no hand-written request/response types.
- Audit logging: every request is logged at the default `"info"` level as a start/end pair of JSON lines (`{ timestamp, level, message: "request started" | "request completed", requestId, method, path, user, status, durationMs }` — `status`/`durationMs` only on the "completed" line, `user` being the authenticated user id or `"anonymous"`), joined by a per-request `requestId` (`c.set('requestId', ...)`, an 8-hex-char id from 4 random bytes — short enough to scan by eye, not a full UUID) since concurrent requests to the same method+path would otherwise be indistinguishable in the log stream. This middleware wraps the auth guard, so a rejected (401) request is logged too, not just successful ones, and it's on by default, not opt-in, so it can't be silently disabled by lowering the log level.
- Auth: sign-in first, consent and registration after (root `AGENTS.md` "Sign in with Google and terms consent"): `POST /api/auth/google` verifies a Google ID token (`src/auth/google.ts`) and, for a registered account only, sets a stateless session cookie; an unregistered one gets `{ registered: false }` and is created by `POST /api/auth/register` (the ID token again plus the agreed `TERMS_VERSION`). The cookie is an HS256 JWT (`src/auth/session.ts`), so authenticating a request reads no DB rows. The guard (`repository/auth-guard.session.ts`) applies to every route except `PUBLIC_PATHS`; a session whose agreed terms version is older than `TERMS_VERSION` only reaches the consent-free paths (`CONSENT_FREE_PATHS` in `app.ts`). Hono's `csrf` middleware rejects cross-site form posts.
- Cron work lives in `src/jobs.ts` (notification sending, purge of logically deleted data); the runtime package's scheduled handler calls it. Web Push (`src/push/web-push.ts`) uses WebCrypto only.
- Times and ids come from an injected `Runtime` (`service/context.ts`) so tests can pin them; dates are judged with `packages/utils` helpers in JST.
